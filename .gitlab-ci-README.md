# GitLab CI/CD Configuration

This file provides information about the GitLab CI/CD pipeline configuration in `.gitlab-ci.yml`.

## Pipeline Overview

The pipeline runs automatically on every push and merge request, executing 5 stages:

1. **lint** - Code quality and formatting
2. **test** - Test suite execution
3. **security** - Security scanning
4. **build** - Package building
5. **report** - Coverage reporting and GitLab Pages

## Stages Breakdown

### Stage 1: Lint

**Jobs:**
- `lint:black` - Check code formatting with Black
- `lint:ruff` - Lint code with Ruff
- `type-check:mypy` - Type checking with MyPy (allowed to fail)

**Purpose:** Ensure code quality and style consistency

### Stage 2: Test

**Jobs:**
- `test:python3.13` - Run tests on Python 3.13 with coverage
- `test:python3.14` - Run tests on Python 3.14 (manual, allowed to fail)

**Coverage:** Results are displayed in merge request UI

### Stage 3: Security

**Jobs:**
- `security:safety` - Check dependencies for vulnerabilities
- `security:bandit` - Static security analysis of Python code

**Note:** Both jobs are allowed to fail to not block the pipeline

### Stage 4: Build

**Jobs:**
- `build:package` - Build Python package (wheel + sdist)

**Triggers:** Only on `main`, `develop`, `tags`, and merge requests

### Stage 5: Report

**Jobs:**
- `report:coverage` - Generate final coverage report
- `pages` - Publish coverage to GitLab Pages (main branch only)

**GitLab Pages URL:** `https://<username>.gitlab.io/<project>/`

### Pipelines
- Go to: **CI/CD → Pipelines**
- Click on pipeline status badge
- View individual job logs

### Coverage
- View in merge request UI (Coverage tab)
- GitLab Pages: `https://<username>.gitlab.io/<project>/`
- Download artifacts from job page

### Artifacts

All artifacts are retained for 30 days (7 days for security reports):

- HTML coverage reports
- Coverage XML (Cobertura format)
- Built packages (dist/)
- Security scan reports
- Requirements.txt

## Caching

The pipeline caches:
- pip packages (`.cache/pip`)
- Poetry packages (`.cache/pypoetry`)
- Virtual environment (`.venv`)

**Cache key:** `${CI_COMMIT_REF_SLUG}-${CI_JOB_NAME}`

**To clear cache:**
1. Go to: **CI/CD → Pipelines**
2. Click **Clear runner caches**

## Local Testing

Run the same checks locally before pushing:

```bash
# Quick check

# Fix issues automatically
task ci-fix

# Individual checks
task format        # Format code
task lint          # Lint code
task type-check    # Type checking
task test-cov      # Tests with coverage
```

## Troubleshooting

### Pipeline Not Starting

**Check:**
- CI/CD is enabled: **Settings → CI/CD → General pipelines**
- `.gitlab-ci.yml` exists in repository root
- YAML syntax is valid: Use GitLab CI Lint
- Runners are available: **Settings → CI/CD → Runners**

### Job Failures

**Common issues:**
- Poetry installation fails: Check `POETRY_VERSION` variable
- Tests fail: Run `task test` locally to debug
- Cache issues: Clear runner caches
- Dependencies outdated: Run `poetry update`

### Coverage Not Showing

**Check:**
- `coverage.xml` artifact exists in job
- Coverage report format is Cobertura
- Regex pattern matches in `test:python3.13` job
- Pipeline passed on the branch

### GitLab Pages Not Publishing

**Requirements:**
- Pipeline runs on `main` branch
- GitLab Pages is enabled in project settings
- `pages` job completes successfully
- `public/` directory contains `index.html`

**Check:**
1. Go to: **Settings → Pages**
2. Verify Pages is enabled
3. Check access control settings

## Pipeline Optimization

### Speed Up Pipelines

1. **Use cache effectively:**
   - Ensure `poetry.lock` is committed
   - Cache keys are stable

2. **Limit test matrix:**
   - Python 3.14 is manual-only
   - Add more versions sparingly

3. **Parallel jobs:**
   - Jobs in same stage run in parallel
   - Ensure enough runners available

### Reduce Resource Usage

1. **Artifact retention:**
   - Adjust `expire_in` for artifacts
   - Download only when needed

2. **Job optimization:**
   - Skip jobs on certain branches
   - Use `only`/`except` rules wisely

## Best Practices

1. ✅ **Always run local checks before pushing**
   ```bash
   task ci
   ```

2. ✅ **Fix linting issues immediately**
   ```bash
   task ci-fix
   ```

3. ✅ **Review coverage reports**
   - Aim for >80% coverage
   - Check uncovered lines

4. ✅ **Monitor security scans**
   - Review Safety reports
   - Update vulnerable dependencies

5. ✅ **Keep dependencies updated**
   ```bash
   task update
   ```

6. ✅ **Tag releases properly**
   ```bash
   git tag -a v1.0.0 -m "Release version 1.0.0"
   git push origin v1.0.0
   ```
